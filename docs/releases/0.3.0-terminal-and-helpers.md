# Eggent 0.3.0 - Terminal and Helpers

Date: 2026-10-09  
Type: Minor release snapshot

## Release Name
`Terminal and Helpers`

You can now run commands from the chat and keep a real terminal open beside
it. Helpers the agent starts report back inside the turn that started them and
show their work as they go. Telegram answers appear as they are written.
Deleting one scheduled task no longer deletes the rest.

Nothing needs migrating.

## What Is Included

### 1) Commands from the chat

- A **Run** button appears under a finished message's shell code blocks
  (`bash`, `sh`, `shell`, `zsh`, or a `console` block where every line is a
  `$` prompt). It is withheld from a message still streaming, because the first
  lines of a script are another script.
- A message starting with `!` runs as a command. `!!x` sends a message that
  starts with `!`. `!cmd` works while a turn is running.
- Output streams into a card anchored under the message; it is kept in
  `sessionStorage` only, so what a command printed does not outlive the tab.
  Nothing reaches the agent unasked: **Show to the agent** sends a normal
  message with the command and its output.

### 2) A terminal panel

- One terminal per project, opened from the header, on every screen that has
  the files panel. Resizable, remembered width, light and dark palettes; on a
  phone it covers the chat.
- The pty is a small Python helper (`pty.fork()` plus a select loop) rather than
  a native module. Without Python the server answers `501` and the panel says
  that commands still run from the chat; there is no degraded mode.
- Transport is server-sent events out and plain POSTs in. A reader attaches at
  an offset, so a dropped connection resumes where it stopped and a reload
  replays up to 1 MB of output.
- Authentication is checked in every handler, not only the middleware. Writes
  need `application/json`, a same-site origin and a session that is not the
  default login, because sibling workspaces share a registrable domain.
- Lifetimes: a terminal closes after 30 minutes with no input and no output, or
  with no reader; a run is stopped after 60 minutes; finished jobs are kept 15
  minutes. At most 8 runs and 3 terminals. A slow reader is let go past 4 MB
  queued and comes back with its offset.

### 3) Helpers (subagents)

- pi-subagents detaches by default and delivers results by starting a new turn in
  the parent session, which Eggent disposes when the turn ends. Helpers
  launched that way finished for nobody, or never started.
- Every Agent call without a schedule now runs in the foreground: calls in one
  message run in parallel, and the parent continues with every result in the
  same turn. At most six per turn; a seventh is refused with a reason the model
  reads. Scheduled helpers are untouched.
- Each helper has a row: what it is doing now, steps, time, then its task,
  steps with targets (secrets masked) and result. A reload draws the same cards.
- Disposing a session stops unfinished helpers and waits for their answer.

### 4) Telegram

- Answers are written into a draft while they are generated, then sent as a
  normal message. Until the answer starts the draft shows what is happening and
  how many helpers are still working.
- A reply goes to the chat it answers; anything else goes to the chat that wrote
  last, and an answer from another conversation ends with its title. `/chats`
  and `/c_<id>` list and switch. `eggent_manage_chats` lets the agent list,
  search, read, switch and create.
- Each scheduled run reports into a chat of its own, one per task and day,
  marked with a clock in the sidebar. The run itself is unchanged.

### 5) Schedules

- `clear` ignored `job_id`, so deleting one task deleted every task in scope,
  from the agent's tool and from the Schedules page alike. It now deletes the
  task and re-arms only the session that held it.
- A session that owns a schedule is shut down properly before it is disposed, so
  timers no longer outlive their session and fire against a stale context.
- A reload re-arms a session bound beyond its mode, and every session logs
  extension handler errors. A stopped chat keeps its schedules.

### 6) Questions and cards

- A turn waiting on `eggent_ask_user` is stored while it waits, so a reload or a
  restart no longer loses the question. Stop sits beside a waiting question
  card. A card with buttons accepts a typed answer.
- On a confirm card the first option means yes and the rest mean no.

### 7) Start-up, sign-in and files

- The default pi packages are installed into the image at build time with pinned
  versions and copied into a new workspace: about 2.4 s instead of about 25 s,
  and a fresh container answers `/api/health` in about 9 s instead of about 31 s.
- `POST /api/auth/handoff` issues a one-time sign-in link, valid once and for 10
  minutes, kept only as a hash. The login page removes it from the address bar
  before spending it.
- The file tree keeps its open folders across pages; the files panel stays beside
  the settings tabs under the header.
- The agent asks before a large install and puts tools inside the project, where
  the Files panel shows them.

## Platform Coverage

- Web UI: Run cards, `!` commands, terminal panel, helper rows, file tree.
- API: `/api/terminal/jobs/**`, `/api/auth/handoff`, event-stream responses on
  the external routes.
- Runtime: helper policy, scheduled-run chats, Telegram drafts and routing.

## Upgrade Notes

- Compatibility: the terminal needs `python3` (present in the image). No Windows
  support for the terminal yet.
- Migration: none.
- Operational changes: `EGGENT_TERMINAL_IDLE_MINUTES`,
  `EGGENT_TERMINAL_DETACH_MINUTES`, `EGGENT_TERMINAL_RUN_MAX_MINUTES`,
  `EGGENT_TERMINAL_PYTHON`, `EGGENT_TERMINAL_ROOT` are optional.
