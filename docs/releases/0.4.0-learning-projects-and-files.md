# Eggent 0.4.0 - Learning, Projects and Files

Date: 2026-10-11  
Type: Minor release snapshot

## Release Name
`Learning, Projects and Files`

The agent can keep short notes and write skills from what you tell it and what
it does. A project can be asked for help by name with `@project`. A folder, or
the files an answer made, comes down in one click, and Telegram has `/files`.
A turn that goes quiet is stopped instead of waiting for ever, a scheduled task
that cannot run is paused instead of firing for ever, and credentials you paste
are hidden in stored chats.

Nothing needs migrating.

## What Is Included

### 1) The agent learns

- After a turn that gives a reason, a short look-back may keep something. The
  reasons are plain facts about the turn: you asked it to remember, you
  corrected it, an error was got past, it did a long piece of real work with no
  skill in sight, or - for notes only - every sixth turn. A conversation that
  shows none of these is not looked at after every sentence.
- Two things are kept, both beside the orchestrator's files so they travel with
  them: `learned.md` (`## About you`, up to 1400 characters, and `## Notes`, up
  to 2200, at most 30 notes of 300 characters) and skills marked
  `origin: learned` in `skills/`. Notes are read into the system prompt at the
  start of each turn, so a note written during turn N is used from turn N+1.
- The look-back is a fresh session with two tools and no others: `memory` (add,
  replace, remove) and `skill_manage` (view, create, patch, write a support
  file). It is stopped after 8 tool calls or 120 s, runs at least 60 s after the
  previous one and at most 40 times a day, and can use a cheaper model
  (`EGGENT_LEARNING_MODEL`). Each look-back leaves one line in the log.
- Every write is checked first. Credentials, text that overrides the assistant
  or hides things from the person, a role change (in notes), an address beside
  "send" and invisible characters are refused with a reason, and a note nearly
  identical to an existing one is refused with that note named.
- The agent changes only skills it wrote itself. A skill you made, or an
  installed bundled one, is read-only to it.
- A learned skill unused for 30 days is marked stale and moved to
  `skills/.archive/` at 90. Nothing is deleted.
- What was kept is quoted under the answer, and Telegram gets one short message.
  **Settings -> Memory -> What the agent has learned** lists the notes, removes
  one by its text, adds one and switches learning off. `EGGENT_LEARNING=off`
  turns the whole feature off, including the notes block in the prompt.

### 2) Skills: upload and delete

- **Settings -> Skills -> Upload skill** takes a `SKILL.md`, a `.zip` or a
  `.skill` archive, several at once, into the scope chosen in the selector (the
  orchestrator or one project). Limits: a 30 MB archive, 600 files, `SKILL.md`
  up to 512 KB.
- Everything is judged in memory before a byte is written, so a refusal leaves
  nothing behind. The header is read with the same YAML library the runtime
  uses: pi drops a skill whose header is not valid YAML without a word, so such
  a skill is refused with the reason instead of installing and never showing up.
- The archive reader is Eggent's own: central directory first, every entry
  checked for size and CRC, paths with `..`, absolute paths, links and devices
  refused, `__MACOSX` and `._*` files dropped. ZIP64, split, encrypted and
  non-deflate archives are refused by name.
- A name that already exists is a question, not an overwrite. **Replace** moves
  the old folder to `skills/.replaced/<name>-<date>` and puts the new one in; a
  failed swap puts the old one back.
- A skill marked `origin: learned` loses the mark on upload, because the agent
  may change only the skills it wrote.
- Each installed skill has a delete button (with the usual confirmation). It
  removes the folder, every older copy of it and the versions a replacement put
  aside. The name's shape is checked first: a name such as `../notes` used to
  remove whatever it pointed at.
- `POST /api/projects/:id/skills/upload` (one file per request) and
  `DELETE /api/projects/:id/skills` (`{name}` in a JSON body) need a signed-in
  session and a same-site origin.

### 3) Asking a project

- `@shop how many orders came back?` hands the task to the project `shop`. A
  project is found by its id or its name; spaces, hyphens, underscores and case
  do not matter (`My Shop`, `my-shop` and `myshop` are one), and the name must
  be followed by whitespace, `:` or `,`. A handle that is not a project (a
  Telegram username, an address, a mention in the middle of a sentence) is an
  ordinary message, and two projects that fit are asked about.
- The project does the work with its own files, skills, `.mcp.json`,
  instructions and model, in a chat of its own - one per conversation and
  project, marked with an arrow in the project's chat list. The answer comes
  back in the same turn as the project's reply, which the parent relays. The
  active project and the conversation do not move.
- It works in the web composer (typing `@` opens the other projects with their
  descriptions, and a line above the field says whom you will ask), in Telegram
  and through the external API. The card in the chat is the helper card: what
  the project is doing now, what it ran, the answer, and a link that opens the
  project.
- Only your own `@` starts a visit. A page or a file the model read cannot make
  it ask another project, and a visit cannot start another visit. At most two
  visits run at once (`EGGENT_VISITS_MAX`), a visit times out after 10 minutes
  (`EGGENT_VISIT_TIMEOUT_MINUTES`), and Stop reaches into the project. One that
  will not stop is let go of after 20 seconds
  (`EGGENT_VISIT_STOP_GRACE_SECONDS`), so its place is released.
- A visit is quiet: it does not learn, runs at most two helpers, and what it
  sends to Telegram is attributed to the chat that asked. Files a project made
  are listed under the asking chat's answer.
- A project is a place to work, not a sandbox: the agent's built-in shell and
  file tools can reach other paths.

### 4) Turns that go quiet, and `/reset`

- A turn can be stopped from its first line. Before, a turn stuck while its
  session was being built was beyond every stop, because nothing knew it
  existed; and while a turn was starting, compacting or running hooks the
  registry could drop it as idle, so a stop reported success and stopped
  nothing. A stand-in is now registered for the whole turn, a steer sent before
  the session exists is queued and handed over when it starts, and a stop asked
  for before the agent runs is applied the moment it does.
- A watchdog watches the silence. After 90 s with no event it reports it (a
  `silent` event on the event stream and a "still working, send /reset" line in
  the Telegram draft), and it stops the turn after 3 minutes while starting, 6
  with the model silent and 20 inside a tool, saying why. Tools that run side by
  side are counted, so one finishing does not shorten the allowance of a slow
  one, and it never fires while a question is waiting.
  `EGGENT_TURN_WATCHDOG=off` and `EGGENT_TURN_SILENCE_{SOFT,START,MODEL,TOOL}_SECONDS`
  adjust it; a slow local model may need it off.
- `/reset` in Telegram stops the turn, drops a question nobody can answer and
  keeps the conversation. It is answered without the model. The external
  message route takes `controlOnly`: the message must reach a running turn or
  nothing, which lets a messaging front end forward stop words and `/reset`
  while a turn is in flight. A stopped turn answers `stopped: true` with an
  empty reply.
- A run with nobody to answer (the external API, a schedule) no longer waits for
  ever: dialogs are answered "no" and a command that reads standard input gets
  it closed once. An unapproved project MCP server is denied silently instead
  of holding the turn.
- A stopped turn that has not begun is no longer a turn to join: what you say
  next starts a turn of its own instead of being "added" to one that is about to
  end.
- A bot connected by long polling reads messages one after another, so `/reset`
  or "stop" sent during a long turn is read when the turn ends; with a webhook it
  is read at once.

### 5) A task that cannot run is paused

- Runs are counted per task. After five failed runs in a row - three when the
  model endpoint reports a refused request, recognised by a response id that
  starts with `eggent_limit_` - the task is paused (`enabled: false`, marked as
  paused by Eggent, with the reason) and you are told once. A first refusal is
  delivered as the report it is and repeats stay in the run's chat; the first of
  any other failure is announced when the run had no report of its own. The
  notice is also appended to that chat's agent session, so replying "resume it"
  reaches an agent that knows what happened.
  `EGGENT_SCHEDULE_PAUSE_AFTER_REFUSED` and `EGGENT_SCHEDULE_PAUSE_AFTER_FAILED`
  change the counts.
- `eggent_manage_schedules update` takes `enabled`, `POST /api/pi-schedules`
  takes `pause` and `resume`, and the Schedules page shows why a task is paused
  with a Pause / Play button. Resuming clears the count and, if the session that
  owned the task was let go, brings one up.
- A scheduled run's report turn can no longer create, change or delete tasks:
  `update` and `clear` are refused for a session that is running a scheduled
  task, and the Agent tool is blocked with `schedule` there. Listing stays
  allowed. Before, a run could delete its own task or rewrite it.
- The scheduler's registries (retained sessions, lent sessions, pending
  reloads, runs in progress) are one per process; Next compiled the boot hook
  and each route separately and each had its own empty copy.
- A session kept for its schedules serves the chat's next turn with that turn's
  run id, stop signal, question stream and origin. Before, a question asked in
  that turn had no card, and a stopped turn's aborted signal made every later
  scheduled command fail.

### 6) Files out of the workspace

- Every folder row in the file tree, and the root, has a download button. The
  archive is streamed (a large folder costs a few buffers, not the container's
  memory) with per-entry compression, Unix modes and UTF-8 names.
  `GET /api/files/zip?project=<id|none>&path=<folder>`; repeat `path=` for a set
  of files, add `check=1` to learn what it would hold, and `HEAD` answers the
  headers and holds nothing.
- The walk decides what goes in. Links are never followed (a folder on the way
  that is a link out is refused, and so is a project whose folder is a link),
  and a file with a second name is left out. Files that hold credentials
  (`.env*`, `.mcp.json`, `auth.json`, key and certificate files, cloud and
  service-account credentials, `kubeconfig`, `*.tfvars`, ssh keys) and
  credential folders (`.ssh`, `.aws`, `.gnupg`, `.kube`, `.docker`, `.azure`,
  `.gcloud`) are left out and counted, also when named outright and in any case.
  Dependencies and runtime state (`node_modules`, `.git`, `__pycache__`, `.pi`,
  `.cache`, `.next`) are skipped.
- Limits: 1 GiB, 10 000 files and 20 levels (`EGGENT_ZIP_MAX_MB`,
  `EGGENT_ZIP_MAX_FILES`), refused with the reason before anything is sent. One
  archive is made at a time, and one that stands still for 120 s is dropped and
  its place given back (`EGGENT_ZIP_IDLE_SECONDS`).
- The plan can be minutes old and the folder belongs to an agent with a shell,
  so each file is checked again when its turn comes: opened without following
  links and without blocking (a pipe swapped in after the plan cannot hold the
  place for ever), it must be a plain file with one name, and its real path must
  be inside the folder and be the very file that was opened. Anything else is
  skipped.
- **The files an answer made** are listed under it (`GET /api/files/stat` hides
  a file that is gone): a plain file inside the working folder, written during
  the turn, that is not the agent's housekeeping and not a credential file.
  Sources, in order: paths the answer names, `write` calls, `edit` calls the
  answer names, images from the generation tool; a scan for files born during
  the turn is the last resort. The row shows five, "+N more" and one archive of
  the lot, with Open, Download and **Send to Telegram** (`GET` and
  `POST /api/files/telegram`), which goes to the chat that last wrote to the
  bot.
- In Telegram an answer that made files ends with a line naming them, and
  `/files` (answered without the model) sends them: up to three as documents or
  photos, more as one archive per folder, and "Sent 5 of 40 files" when the
  message kept fewer than were made.

### 7) Credentials in chats

- A message that looks like a credential gets a notice before it is sent - what
  is kept, and where the right place is (a bot token belongs in Messengers, a
  model provider key in Models) - with **Send anyway** and **Edit**. It warns, it
  does not block: sometimes the agent has to be given the key. The spoken form
  ("the password is ...") needs a label and a value of at least 8 characters
  with a letter and a digit, so "the password is correct" does not interrupt
  anyone.
- Stored chats hide them (`[hidden key]`, `[hidden token]`, `[hidden private key]`
  and so on) when a chat is saved and when one is read, so a chat synced from an
  older build is hidden on the way out. The shapes: vendor key prefixes, bot
  tokens, code-hosting, cloud and chat-app tokens, signed tokens, private keys,
  links with a password in them, bearer headers, labelled values (`api_key=...`,
  also inside an environment variable's name), and a value kept under a name that
  says what it is (`password`, `token`, `Authorization`, a name ending in
  `_API_KEY`) in what the agent sent to a tool. A name written in code
  (`api_key = settings.client_key`) is an example, not a key, and is left alone.
- The agent's own working memory (`data/pi-sessions`) is not changed, so a key
  you gave it for a task keeps working.
- Older chats are cleaned once, at the first start after the update
  (`data/secrets-sweep.json`). A chat in use is left for its own next save and
  listed for a second look; a chat found clean is not walked again until its file
  changes.
- Every pattern costs time in proportion to the text it reads, so a page the
  agent fetched cannot stall a save. Each shape is fed 150 KB of hostile text in
  the tests.

### 8) Hardening found by review

Two independent reviews of this release's work - fresh readers who were given
the diff and told to break it - found real defects, and the second round found
some in the first round's own fixes. Each has a test that fails on the old
code.

- A chat opened in public mode through the external API was handed every Eggent
  tool (switching project, the schedule manager, Telegram, memory) because
  `enableEggentTools: false` never reached the session. It no longer is. The
  runtime's own file and shell tools are still available in such a chat.
- A throw while a turn was being set up (saving the message, listing projects,
  building the session) left a registered stand-in that made every later message
  "added to the running turn". A failed start now undoes what it registered.
- The credential patterns were quadratic in places - 200 KB of `a.a.a.` took 31
  s - and are linear now.
- The archive and the card under an answer hold up against a folder that
  changes while they are read (see 6).
- The boot sweep of old chats does not rewrite a chat that is being written, and
  a file stamped a hair ahead of the clock is young, not old.

### 9) Tests

New: `test:learning` (52), `test:learning-review` (18), `test:learning-session`
(10), `test:skill-upload` (61), `test:skill-delete` (19), `test:schedule-health`
(17), `test:refusal-responses` (3), `test:session-rebind` (7),
`test:turn-control` (16), `test:turn-watchdog` (14), `test:no-listener-prompts`
(5), `test:stalled-turn` (21), `test:telegram-reset` (9),

The learning, turn, project, file and credential tests drive the real runtime
against a stub model provider, and most of them were mutation-checked: with the
fix removed they fail. All 56 `test:*` scripts pass.

## Platform Coverage

- Web UI: `@` project menu and card, learned-note quotes and Settings -> Memory,
  Upload skill and delete, file cards and folder download, credential notice,
  Pause and Play on the Schedules page.
- API: `/api/files/zip`, `/api/files/stat`, `/api/files/telegram`,
  `/api/learning`, `POST /api/projects/:id/skills/upload`,
  `DELETE /api/projects/:id/skills`, `pause` and `resume` on
  `/api/pi-schedules`; the external message route gains `controlOnly` and
  answers `stopped`.
- Telegram: `/reset`, `/files`, `@project`, and a hint under an answer that made
  files.
- Runtime: learning look-backs, turn watchdog, project visits, schedule health,
  credential masking in the chat store.

## Upgrade Notes

- Compatibility: nothing is removed or renamed. `yaml` 2.9.0 is now a direct
  dependency (the version the SDK already pins).
- Migration: none. The first start after the update scans stored chats once;
  `learned.md` appears when the agent first keeps something.
- Operational changes, all optional: `EGGENT_LEARNING`, `EGGENT_LEARNING_MODEL`,
  `EGGENT_LEARNING_MIN_GAP_SECONDS`, `EGGENT_LEARNING_DAILY_CAP`,
  `EGGENT_LEARNING_STALE_DAYS`, `EGGENT_LEARNED_USER_CHARS`,
  `EGGENT_LEARNED_NOTES_CHARS`; `EGGENT_TURN_WATCHDOG`,
  `EGGENT_TURN_SILENCE_SOFT_SECONDS`, `EGGENT_TURN_SILENCE_START_SECONDS`,
  `EGGENT_TURN_SILENCE_MODEL_SECONDS`, `EGGENT_TURN_SILENCE_TOOL_SECONDS`,
  `EGGENT_TURN_WATCHDOG_TICK_MS`; `EGGENT_VISITS_MAX`,
  `EGGENT_VISIT_TIMEOUT_MINUTES`, `EGGENT_VISIT_STOP_GRACE_SECONDS`;
  `EGGENT_ZIP_MAX_MB`, `EGGENT_ZIP_MAX_FILES`, `EGGENT_ZIP_IDLE_SECONDS`;
  `EGGENT_SCHEDULE_PAUSE_AFTER_REFUSED`, `EGGENT_SCHEDULE_PAUSE_AFTER_FAILED`.
- Known limits: a bot connected by long polling reads messages one at a time; a
  project is a place to work, not a sandbox; a chat in public mode still has the
  runtime's own file and shell tools; **Send to Telegram** goes to the chat that
  last wrote to the bot, which with several people allowed on one bot may not be
  yours.
