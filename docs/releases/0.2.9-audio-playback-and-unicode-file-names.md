# Eggent 0.2.9 - Audio Playback and Unicode File Names

Date: 2026-09-28  
Type: Patch release snapshot

## Release Name
`Audio Playback and Unicode File Names`

A recording the agent makes can now be played where it is named: in the
answer, and on the file's own screen. Underneath that, three things had been
failing silently. A file whose name used any script beyond Latin-1 could not be
downloaded at all. Audio was served in a form no browser plays. And every file
link in an answer was drawn again from scratch whenever the window regained
focus.

Nothing needs migrating.

## What Is Included

### 1) Audio plays in the chat

- An agent asked to voice one line in four moods wrote four `.mp3` files and
  answered with a table of their paths. Nothing in the product could play
  them: the paths were plain text, and the files could only be downloaded.
- A relative path to an audio file in inline code - `tts/take-1.mp3` - and a
  markdown link or embed pointing at one now render as a small player: play
  and pause, the length and then the time played, a thin progress line, and
  the path itself linking to the file's own screen. The path is checked against
  the directory listing first, like any other file mention, so a path to a file
  that does not exist stays plain text.
- One recording plays at a time. Starting a take pauses the one before it,
  which is what comparing takes needs.
- Recognised types: `.mp3`, `.wav`, `.ogg`, `.oga`, `.opus`, `.m4a`, `.aac`,
  `.flac`. Raw PCM has no header a browser could decode, so it is not included.
- If the browser cannot decode a file, the player gives way to the plain link.

### 2) The file screen plays audio

- Opening an audio file from the Files panel showed "Binary files cannot be
  previewed as text". It now shows the browser's own player - seeking, volume
  and speed - with the download button beside it, the way an image shows its
  preview.

### 3) Downloads

- **A file whose name used characters beyond Latin-1 could not be
  downloaded.** The name went into `Content-Disposition` as written. Header
  values are byte strings, so the `Response` constructor threw and the route
  answered `404 File not found`. That happened for every such file, audio or
  not, whether it was downloaded from the file tree, the Files page or a link
  in the chat. The name is now sent as `filename*=UTF-8''...`, with an ASCII
  fallback in `filename`.
- `GET /api/files/download` answers `Range` requests with `206 Partial
  Content` and streams the file from disk instead of reading it whole. Safari
  plays nothing from a server that answers its first `bytes=0-1` request with
  the whole file, and no browser can seek without ranges.
- Audio opened with `inline=1` is served with its own content type
  (`audio/mpeg`, `audio/wav` and so on) instead of `text/plain` under
  `nosniff`.
- The path check no longer accepts a sibling directory whose name only starts
  like the project's own, such as `../projects.json` next to `projects`.

### 4) Answers are no longer drawn again on every render

- The chat's markdown renderers were a new object on every render.
  react-markdown uses them as component types, so everything they drew was
  unmounted and mounted again whenever the chat re-rendered, and a window
  regaining focus was enough to cause that. File links flashed back to plain
  code for a moment, and a playing recording would have stopped. The renderers
  are now built once per project.

### 5) Skills and Telegram

- A bundled skill can declare `launch_scope: orchestrator` in its frontmatter,
  and its quick-start card then launches in the orchestrator instead of in a
  new project of its own. Before, only a list of names kept in core could do
  that, so a deployment adding such a skill needed a new core.
- The Telegram tool's `status` names the connected bot, with its link, or
  quotes Telegram's answer when the stored token is rejected. It also says
  whether the current run came in over Telegram. The tool's description sends
  people to the settings page for the token rather than inviting them to paste
  it into the chat.

### 6) Tests

- `npm run test:chat-audio` runs the real download and content routes against
  a real directory. It covers ranges, a non-Latin name, a missing file, a
  folder, a way out of the project and a sibling with a similar name. It also
  checks which paths in an answer become players, through the real markdown
  pipeline. Eight of its checks fail against the 0.2.8 routes.
- `npm run test:skill-launch` covers the `launch_scope` key.

## Platform Coverage

- Web UI: an audio player in answers, and audio playback on the file screen.
- API: `GET /api/files/download` supports `Range`, streams from disk, serves
  audio types inline and encodes non-ASCII names; `GET /api/files/content`
  returns a playable preview URL for audio files.
- Runtime: the `launch_scope` frontmatter key for bundled skills; the Telegram
  tool's status.

## Upgrade Notes

- Compatibility: download responses now carry `Accept-Ranges: bytes` and
  `Content-Length`, and a `filename*` parameter beside `filename`. A client that
  sends no `Range` header gets the whole file, as before.
- Migration: none.
- Operational changes: none.
