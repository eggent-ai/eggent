# Eggent 0.2.2 - Document Toolbelt and Project Routing

Date: 2026-08-25  
Type: Patch release snapshot

## Release Name
`Document Toolbelt and Project Routing`

The agent can now open the files people actually send it, and it stops being
silent about where things went. Both come from the same observation: the
workspace was doing the right thing internally and failing to say so, or failing
at the last step for want of a library that costs twelve megabytes.

## What Is Included

### 1) Working with documents

- **The image ships a document toolbelt.** Pillow, pandas, openpyxl, python-docx,
  python-pptx, pypdf, pdfplumber, beautifulsoup4, lxml, oletools, chardet,
  dnspython and psycopg2, plus the command line tools a document task reaches
  for: `unzip`, `zip`, `pdftotext`, `file`, `strings`, `xxd`, `make`, `wget`,
  `ps`, `host`.
- Until now the agent reached for the obvious library, got
  `ModuleNotFoundError`, and installed it by hand at the user's expense - ten
  shell calls to read one scanned PDF. Worse, the install lived in the
  container's writable layer and was gone after the next recreate, so the same
  work happened again.
- The image grows by about 286 MB. `matplotlib` is deliberately left out: it is
  74 MB against three observed misses, and hand-written SVG already works.

### 2) The shell the agent runs in

- **The terminal runtime no longer starts a login shell.** It used to, and
  Debian's `/etc/profile` assigns `PATH` outright rather than adding to it, so
  the interpreter shipped in the image - and everything installed into it -
  disappeared inside the command.
- The two shells disagreed as a result: the runtime's own `bash` tool spawns
  without a login shell and saw the packages, `execute_code` did not, and the
  same import failed in one tool and worked in the other. They now behave the
  same. The login shell's own `PATH` is still merged in, so anything a profile
  adds is kept.

### 3) Models and providers

- **A saved key that did not become the model now says so.** Saving a provider
  key and moving the workspace onto it are two steps, and the second could fail
  in silence: both failing paths returned the settings unchanged and the API
  answered 200 with them, so a key that took effect and one that did not looked
  identical.
- The settings screen reports which happened - switched, or saved while the
  workspace still answers on its previous model. The same silence on OAuth
  sign-in and on deleting the credential in use is closed too.

### 4) Skills and projects

- **A quick-start card starts the work instead of asking where to put it.** The
  skill gets its own project, named after the card and identified after the
  skill on disk. Skills that describe the workspace rather than a line of work
  stay in the workspace scope, where every chat can read what they wrote.
- **A new project announces itself.** One row is added to a routing table in the
  workspace context file - project, id, what it is for - so someone can keep
  working in the workspace scope and the agent moves to the right project when
  a message belongs there. It stays a routing table: that file is read on every
  message, so a row says where the work lives and never what is in it.

## Upgrade Notes

- **Compatibility:** no data migration is required.
- **Migration:** none. Existing projects and installed skills are untouched.
- **Operational changes:**
  - The container image is larger by roughly 286 MB. Pull time grows; the layers
    below are unchanged and stay cached.
  - Docker still binds to `127.0.0.1` by default. Use `APP_BIND_HOST=0.0.0.0`
    only when direct public exposure is intended.
  - Nothing needs configuring for the toolbelt. It is on `PATH` for both the
    `bash` tool and `execute_code`.

## Verification

- `npx tsc --noEmit`
- `npm run test:schedules`
- `npm run test:managed-provider`
- `npm run test:default-model`
- `npm run test:skill-launch`
- Toolbelt exercised in a running container against real files: an XLSX read
  back through pandas, a DOCX written and reopened, a PPTX, a PNG, `pdftotext`
  and `unzip` present.
- Both shells checked in the same container: the same import now succeeds in the
  `bash` tool and in `execute_code`, and fails only in a deliberately started
  login shell.
