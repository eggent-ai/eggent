# Eggent 0.2.8 - Light Chat History

Date: 2026-09-25  
Type: Patch release snapshot

## Release Name
`Light Chat History`

A conversation in which the agent looked at pictures now opens at once. When
the agent opened an image with the `read` tool, the chat kept the picture as
base64, twice, and the chat page downloaded the whole conversation on every
open and every background sync.

Nothing needs migrating.

## What Is Included

### 1) Stored chats keep no picture bytes

- The runtime's `read` tool returns an image as base64, which is how the model
  gets to see it. The chat store kept that tool result twice - on the tool
  message and again on the assistant's timeline - so a 40-message chat in
  which the agent looked at four pictures it had just drawn weighed 13 MB.
- The chat page fetches the open conversation whole, so that chat showed an
  empty transcript for seven to eleven seconds each time it was opened. Any
  agent that checks the pictures it draws produces such a chat.
- The bytes of an image block in a tool result (`{ type: "image", data,
  mimeType }`) are now dropped when a chat is saved and when it is read. The
  block keeps its type and gains `omitted: true` and `bytes`, roughly how large
  the picture was. Everything else in the chat is left as it was, including
  pictures a person attached.
- Nothing read those bytes back. The chat shows a tool's pictures by their file
  path, and the model's context lives in the runtime's own session, not in the
  stored copy of the chat.
- Because the bytes are also dropped on read, chats stored before this release
  open light at once. The file on disk shrinks at its next save.

### 2) An unchanged chat is not downloaded again

- The open chat is fetched again on every background sync: every 30 seconds,
  whenever the window regains focus and whenever the tab becomes visible. For
  the chat above that was 8.6 MB compressed each time - about a gigabyte an
  hour for as long as its tab stayed open.
- `GET /api/chat/history?id=` now answers with a weak `ETag` and
  `Cache-Control: private, no-cache`. The browser revalidates with
  `If-None-Match`, and a conversation that has not changed costs a `304` with
  no body. The dashboard needs no change for this: its `fetch` goes through the
  browser cache, which does the revalidation by itself.
- The tag is weak so that a reverse proxy compressing the response on its way
  out cannot turn every revalidation back into a full download.

### 3) Tests

- `npm run test:chat-media` checks that no copy of a picture survives on either
  message, that the text beside it and a person's own attachment are kept,
  that the input is not mutated and a chat with nothing to drop is returned as
  it was; that a save writes no picture to disk and an older file is read
  without its pictures and left untouched; and that the history route answers
  with a validator, returns `304` for an unchanged chat and the new chat once it
  changes.

## Platform Coverage

- Runtime: stored chats drop the picture bytes in tool results, on save and on
  read.
- API: `GET /api/chat/history?id=` returns an `ETag` and honours
  `If-None-Match`.

## Upgrade Notes

- Compatibility: a client that ignores the new headers sees the same responses
  as before, without the picture bytes. Anything that read a picture out of a
  stored chat's tool results will find `omitted: true` and a `bytes` estimate
  instead; the file the tool read is where the picture is.
- Migration: none.
- Operational changes: none.
