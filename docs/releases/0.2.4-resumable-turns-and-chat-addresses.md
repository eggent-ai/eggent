# Eggent 0.2.4 - Resumable Turns and Chat Addresses

Date: 2026-08-31  
Type: Patch release snapshot

## Release Name
`Resumable Turns and Chat Addresses`

Two things a conversation could not do. It could not outlive the tab it was
started in, and it could not be linked to. Both are the same complaint from the
user's side: the work was there a moment ago and now the screen has nothing on
it.

## What Is Included

### 1) A turn you can walk away from

- A run existed only inside the HTTP response that started it. Click another
  chat, open settings, close the tab, and everything the agent had written was
  gone: the run carried on, but the only copy of its output was being piped into
  a connection nobody was reading. Coming back showed the opening message and
  then nothing at all, for however long the work took.
- The run writes into a buffer now and the response is simply the first thing
  reading it. Whoever attaches next is handed everything so far, in order, and
  then follows along live - the same view the tab that started it has. The
  client side is one call to the AI SDK's `resumeStream()`, against
  `GET /api/chat/<chatId>/stream`, which answers `204` when nothing is running.
- Buffered text is folded as it arrives, so the buffer grows with the answer
  rather than with the tokens it arrived in, and it is dropped the moment the
  turn ends, because from then on the stored conversation is the better copy.
- The chat list marks the conversations that are working - a slow pulse in the
  corner, calmed rather than stopped under `prefers-reduced-motion`, because a
  mark that stops moving reads as one that finished.
- A turn started from Telegram is the same turn, so it records into the same
  buffer and can be watched from the browser as it happens.

### 2) Stopping is something you ask for

- Dropping the HTTP request used to be how a turn was stopped, which made "stop"
  and "I am closing this tab" the same gesture. Only one of them means stop.
- The stop button posts to `POST /api/chat/<chatId>/stop`, which winds the run
  down, and answers only once the half-written turn has been stored - so the
  answer the person just chose to keep does not blink out of existence while the
  file catches up.
- A run that is asked to stop is told so, rather than having its session pulled
  from underneath: a turn stopped before it wrote anything otherwise looks
  exactly like a turn that was never answered, and gets reported as a broken
  provider.

### 3) Every conversation has an address

- Chats had ids all along but no url, so the browser said `/dashboard` whichever
  one was open. A conversation is now `/dashboard/<chatId>`: linkable,
  bookmarkable, reloadable, openable in a second tab, and reachable with Back.
- The chat screen is a layout shared by `/dashboard` and `/dashboard/<chatId>`,
  so moving between the two is not a page load. That matters in the one moment
  they coincide - the first message of a new conversation, which gives it its id
  and its address while the answer is already arriving.
- The project a conversation belongs to is resolved on the server and applied
  with it, because everything else on the screen reads that project, including
  the working directory the next message runs in.
- A link to a conversation that does not exist is deliberately not an error. It
  is the ordinary shape of one that does not exist *yet*, since the first
  message names the conversation on the client and the address follows
  immediately.

### 4) Fixes

- **Reopening a working conversation showed nothing.** Three separate causes,
  all of which had to be fixed before it was reliable: the attach was allowed
  once per run per refresh of the run list and leaving the chat did not forget
  it, so only the *first* visit attached; the decision came only from a polled
  list that nothing about clicking a chat refreshes; and routes settle in the
  order their payloads arrive, so the page for an address already left could
  mount last and assert it. The case that hurt most is a turn waiting on a
  question, because the question lives in the stream and is never stored - so it
  stayed invisible for as long as it waited, and could not be answered.
- The chat avatar now lines up with whatever the message opens with. A tool card
  sat 13px below its centre and a group of them 5px.

## Upgrade Notes

- **Compatibility:** no data migration is required.
- **Migration:** none.
- **Operational changes:** a turn now survives the browser tab closing. It ends
  when it finishes, when the stop button is pressed, or when a stop word is
  sent - navigating away no longer ends it. Docker still binds to `127.0.0.1`
  by default.

## Verification

- `npx tsc --noEmit`, `npm run lint`, `npm run build`
- `npm run test:live-runs`, `npm run test:dashboard-routes`,
  `npm run test:active-runs`
- Behaviour reproduced against a production build with a stubbed slow model
  endpoint, before and after each fix: a connection dropped mid-run and
  reattached to the full replay plus the live tail; a stop that leaves the
  half-written turn on screen and in the stored conversation; four consecutive
  returns to a working conversation, including two where the first navigation
  had almost no time to land, and again with the run list permanently blinded.
- Route resolution checked against the built application: every page under
  `/dashboard` serves itself and none falls through to the conversation route.
